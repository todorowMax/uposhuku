# Semantic HTML and keyboard access

- SEM-1. Every page has the landmarks it needs (`header`, `nav` with `aria-label` when there are two, `main`, `footer`; `aside` and `search` where they fit), exactly one visible `<main id="main">`, and a skip link as the first focusable element. Why: screen reader users jump by landmark, and a second `main` or none breaks that map. Check: review, axe. Example: ukoshiku/app/layout.tsx
- SEM-2. One `h1` per page, headings go down one level at a time and are chosen by structure, not by font size; a reusable component takes a `level` prop instead of hardcoding `h2` or `h3`. Why: headings are the outline users navigate by, and a card fixed at `h3` breaks it wherever it lands. Check: `jsx-a11y/heading-has-content`, review.
- SEM-3. `<html lang>` follows the active locale and every route exports a unique `title` (`metadata` or `generateMetadata`, template in the root layout). Why: the voice, hyphenation and the Next route announcer depend on them. Check: `jsx-a11y/html-has-lang`, review. Example: ukoshiku/app/pricing/page.tsx
- SEM-4. Something that does something is a `<button type="button">` (feature code: `Button`, DS-2); something that goes to a URL is an `<a href>` or `Link`; never `<a href="#">`, never a link inside a button or the reverse (use `Button asChild`), never a clickable card root. Why: native elements bring focus, Enter and Space, a role and new-tab behaviour; nested interactive content is invalid. Check: `jsx-a11y/anchor-is-valid`, `jsx-a11y/anchor-has-content`, review.
- SEM-5. No `onClick`, `onMouseDown` or key handlers on `div`, `span` or other non-interactive elements, and no `role="button"` plus `tabIndex` workaround; change the element. Why: a div with a handler is invisible to the keyboard and to assistive technology. Check: `jsx-a11y/no-static-element-interactions`, `jsx-a11y/no-noninteractive-element-interactions`, `jsx-a11y/click-events-have-key-events`, `jsx-a11y/interactive-supports-focus`, `jsx-a11y/mouse-events-have-key-events`.
- SEM-6. `tabIndex` is `0` or `-1` and nothing else: `-1` for programmatic focus targets (`main`, an `h1`, an error summary), `0` only for a custom widget with no native element; never a positive value, and no `tabIndex` on elements that are already focusable or on non-interactive ones to "make them focusable". Why: a positive value reorders Tab across the whole page and native elements need no help. Check: `jsx-a11y/tabindex-no-positive`, `jsx-a11y/no-noninteractive-tabindex`.
- SEM-7. Focus is managed on purpose: overlays use the shared primitive (DS-5), a route change that replaces the view moves focus to the `h1` or `main`, content that replaces what the user was using receives focus, and `autoFocus` appears only inside a freshly opened overlay or editor with a comment. Why: focus left on a removed link or dumped on `body` strands keyboard users. Check: `jsx-a11y/no-autofocus`, review. Example: ukoshiku/components/ui/dialog.tsx
- SEM-8. Every form control has a visible `<label>` tied by `htmlFor` and `id` (`useId`), a valid `autoComplete` for personal data, related controls in `fieldset` and `legend`, and an error that sits beside the field, is linked by `aria-describedby`, and sets `aria-invalid` only after submit or blur; the controlled wrappers emit all of this once (FORM-1, FORM-4). Why: a field without a programmatic label or error is silent to a screen reader. Check: `jsx-a11y/label-has-associated-control`, `jsx-a11y/autocomplete-valid`, review. Example: Demo/DemoWorkSpace/components/controlled/InputControl.tsx
- SEM-9. Use a native element or a Radix primitive before any `role` or `aria-*`; write ARIA only for a custom widget, following its APG pattern and its keyboard behaviour, and never re-add ARIA to a Radix part. Names come from visible text, then `aria-labelledby`, then `aria-label` (DS-7). Why: a role promises behaviour that ARIA does not supply, and wrong ARIA is worse than none. Check: `jsx-a11y/no-redundant-roles`, `jsx-a11y/aria-role`, `jsx-a11y/no-interactive-element-to-noninteractive-role`, `jsx-a11y/no-noninteractive-element-to-interactive-role`, `jsx-a11y/aria-activedescendant-has-tabindex`. Example: Demo/DemoWorkSpace/components/ui/close-button.tsx
- SEM-10. `aria-hidden="true"` goes only on decorative or duplicated content, never on a focusable element or on a container of one; to remove a region use `hidden`, and to block a visible one use `inert`. Why: keyboard focus lands on something a screen reader cannot see. Check: `jsx-a11y/no-aria-hidden-on-focusable`, review.
- SEM-11. Every `Image`, `<img>`, `iframe` and `video` has its text alternative: `alt` as a decision (a short description when informative, `alt=""` when decorative or repeated by nearby text, the action when it is the only content of a link or button; never "image of"), `title` on an `iframe`, captions on a `video`. Why: a missing alt is read as the file name, and an untitled embed is an unnamed stop. Check: `jsx-a11y/alt-text`, `jsx-a11y/img-redundant-alt`, `jsx-a11y/iframe-has-title`, `jsx-a11y/media-has-caption`, review.
- SEM-12. A result, saved state or loading change that does not move focus is announced through a `role="status"` region that is already mounted (`role="alert"` only for errors that need attention now). Why: without a live region a screen reader user never learns the result arrived. Check: review, axe. Example: ukoshiku/components/assistant/working-status.tsx
