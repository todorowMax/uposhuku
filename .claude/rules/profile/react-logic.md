# React logic

- COMP-1. `app/**/page.tsx` and `layout.tsx` load data on the server and compose components; no `useState` or `useEffect` business logic in them. Why: `register/page.tsx` in Demo held 445 lines, 4 effects and 4 state hooks. Check: ESLint `no-restricted-imports` for `useState`, `useEffect`, `useLayoutEffect`, `useReducer` in page and layout files. Example: ukoshiku/eslint.config.mjs
- COMP-2. A component's own logic (state, effects, data loading, derived values, handlers) goes to `use-<name>.ts` next to it and the component file is markup; trigger: more than three `useState` or any non-trivial `useEffect`. Pure helpers go to `utils.ts` in the folder; a hook moves to `hooks/` once two features use it. Why: logic and markup in one file grew to 1,000-line components. Check: review (no linter counts `useState`). Example: ukoshiku/components/recipe-editor/use-recipe-editor.ts
- COMP-6. `"use client"` goes on the interactive leaf only; a section does not become client-side because one element animates, wrap that element. Why: all ten Demo landing sections were client components and pulled animation code into the first load. Check: review.
- COMP-10. No `any`; use `unknown` and narrow, and validate data from outside (API, storage, URL) with a schema at the boundary. Why: untyped data hides bugs until runtime. Check: ESLint `@typescript-eslint/no-explicit-any` as error.
- COMP-11. A function does one thing; one that does more is split by responsibility, however long, and a long one that does one thing stays whole. Why: mixed responsibilities hide state bugs; length alone does not. Check: review; `sonarjs/cognitive-complexity` (ARCH-7) is the smoke detector, there is no line-count rule.
- COMP-12. React hooks lint findings are fixed by hand, one by one, and never silenced: `react-hooks/rules-of-hooks` is an error, `react-hooks/exhaustive-deps` a warning. Why: a hook after an early `return` and stale closures were found only after the linter was added. Check: ESLint `react-hooks/*`.
- COMP-14. The project names a first-load JS budget per page in its `AGENTS.md` and measures it on the production build. Why: nobody measured Demo's 200 KB budget while the landing pulled in two animation libraries. Check: `next build` First Load JS output, review.
- COMP-15. Functions are arrow functions everywhere: components, hooks, helpers, handlers (`const Name = () => {}`, plus `export default Name` where a default export is required). Exceptions: generators, overloads, code that needs hoisting or `this`. Why: one function form keeps the code uniform and lets a linter enforce it. Check: ESLint `func-style` `["error", "expression"]` and `prefer-arrow-callback`.
- COMP-16. The types of a component live in a type-only namespace inside the component file: `export namespace ButtonTypes { export type Props = …; export type Variant = … }`, used as `ButtonTypes.Props`; no separate types file per component. Why: types sit beside the component that owns them and are used under one name. Check: review.
- COMP-17. Types shared by two or more files go to `<name>.types.ts` or `types/<domain>.ts`, still as `export namespace <Domain>Types`, and are imported with `import type`. Why: shared types get one home without circular imports. Check: ESLint `@typescript-eslint/consistent-type-imports` as error. Example: Demo/DemoAdmin/api/modules.types.ts
- COMP-18. Namespaces contain only `type` and `interface`, never values (`const`, `function`, `enum`), so they stay erasable. Why: a value inside turns the namespace into runtime code that bundles. Check: `tsconfig` `"erasableSyntaxOnly": true` (TypeScript 5.8+), and `@typescript-eslint/no-namespace` switched off (the recommended set forbids namespaces).
