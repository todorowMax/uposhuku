# Контракти оплати USDT (прототип)

**Контракти не проходили аудит і не призначені для справжніх грошей.** Розгортання в справжню мережу: рішення власника після юриста, з аудитом або з жорстким лімітом на угоду (`MAX_AMOUNT`). Папка живе окремо від основного проєкту: свій `package.json`, `knip`, `tsconfig` і ESLint її не чіпають.

## Що тут

- `FeeRouter`: прямий платіж. Виконавець отримує рівно `amount`, отримувач комісії додатково `quoteFee(amount)` (зверху, округлення вгору). Платник схвалює `amount + quoteFee(amount)`. Гроші в контракті не залишаються. Токен з білого списку конструктора, ставка не більше 10 %, ні власника, ні оновлень.
- `EscrowFactory` + `DealEscrow`: окремий контракт-клон (EIP-1167, CREATE2) на кожну угоду. Заказчик одним викликом `createDeal` створює клон і вносить `quoteDeposit(amount)` (ціна плюс комісія зверху). Ставка, отримувач комісії, арбітр, токен, ліміт і строки спору зашиті в реалізацію й незмінні.
- Шлях угоди: `deliver` (виконавець, до `deliverBy` включно) → `release` (заказчик) або `settle` за таймером (будь-хто): без здачі після `deliverBy` гроші йдуть заказчику, після здачі й `reviewEnds` виконавцю. `dispute` відкриває будь-яка сторона; `resolve(pct)` лише арбітр, частка виконавця кратна 5; арбітр поза спором безсилий. Якщо арбітр мовчить `DISPUTE_TIMEOUT`, будь-хто викликає `forceResolve`: правило `FALLBACK_PERFORMER_PCT`, а якщо виплата не проходить через блокування адреси, пробуються «все заказчику», потім «все виконавцю».
- Комісія береться з частки виконавця, невикористана частина внесеної комісії повертається заказчику. Заблокований отримувач комісії виплату не блокує (комісія повертається заказчику; в `FeeRouter` платник її не платить).

## Відомі обмеження (свідомі)

- Спір можна відкрити в будь-який момент до виплати, навіть після спливу таймера: це єдиний вихід, якщо виплата не проходить через блокування. Тому автовиплату варто викликати одразу (це робить `deal-sweep`).
- Токен, надісланий на адресу клона напряму, на угоду не впливає й залишається в клоні назавжди (виведення немає за задумом).
- Якщо Tether заблокує адресу самого клона, гроші цієї угоди заморожені; інші угоди не зачеплено, бо клон окремий.
- `forceResolve` покладається на правило EIP-150 щодо газу; у цій моделі спроби порівнянні за вартістю, тож підмінити результат нестачею газу не вдасться (математично, окремим тестом не перевірено).
- Статичний аналіз (Slither) не запускався: потребує окремої установки Python-інструментів. Фаззинг зроблено детермінованим генератором у тестах, не інструментом.

## Запуск

```
cd contracts
npm ci
npm test                      # hardhat test mocha, усі тести
npx hardhat run scripts/deploy.ts   # локальна мережа Hardhat, розгортає токен-заглушку
npx hardhat build && npx hardhat run scripts/export-abi.ts   # оновити ../lib/crypto/abi
```

## Розгортання (робить власник, не агент)

Параметри лише з оточення, ключів у скрипті немає: `TOKEN_ADDRESS` (звірити зі сторінкою Tether), `FEE_RECIPIENT`, `ARBITER` (мультипідпис Safe на апаратних ключах), `FEE_BPS`, `MAX_AMOUNT`, `DISPUTE_TIMEOUT`, `FALLBACK_PCT`.

Ліміт `MAX_AMOUNT` у найменших одиницях USDT (6 знаків): dev 1000 USDT = `1000000000`, prod 50 000 USDT = `50000000000`. Потолок контракту незмінний, тому на проді він 50 000, а сервер пускає 10 000 (`CRYPTO_MAX_DEAL_USDT` у `wrangler.jsonc`). Підняти сервер до 50 000 можна лише після аудита; вище 50 000 потрібен новий контракт. Мережа описується у `hardhat.config.ts` через `configVariable` (RPC і ключ у сховищі ключів Hardhat, не в файлах), запуск `npx hardhat run scripts/deploy.ts --network <назва>`. У справжній мережі скрипт відмовиться працювати без `TOKEN_ADDRESS`. Після розгортання звірити на оглядачі код і параметри: `FEE_BPS`, `FEE_RECIPIENT`, `ARBITER`, `MAX_AMOUNT`.

## Для сервера (ітерація 5c)

Істина в блокчейні: стан угоди читається з `DealEscrow.state()` (0 не ініціалізовано, 1 внесено, 2 здано, 3 спір, 4 закрито), хто скільки отримав у `paidToPerformer` і події `Closed`. Адресу клона й параметри перевіряти за подією `DealCreated` (`dealRef`, `client`, `performer`, `amount`), а не за словами клієнта. `dealRef` має бути унікальним у межах заказчика.
