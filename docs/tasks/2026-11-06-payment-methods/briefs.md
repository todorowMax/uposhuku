## Итерация 1: лимиты и демо-лица

1. `wrangler.jsonc`: `CRYPTO_MAX_DEAL_USDT` в `vars`: development `"1000"`, production `"10000"`. Комментарий: на проде контракт разворачивается с `maxAmount` 50 000 USDT, поднять сервер до 50 000 можно только после аудита. Значение по умолчанию в коде (1000) не менять: пропущенная переменная не должна поднимать лимит.
2. `contracts/README.md` и пример параметров в `contracts/scripts/deploy.ts`: dev 1000, prod 50 000. Сам деплой запрещён. `.dev.vars.example`: пояснение рядом с переменной.
3. Демо-лица: `scripts/strip-prod-assets.mjs` удаляет `.open-next/assets/map/faces` и сообщает, что удалил, отсутствие каталога не ошибка. `cf:deploy:production` вызывает его перед `opennextjs-cloudflare deploy`. `public/map/faces` и dev-сиды не трогать. Проверить, что `deploy` не пересобирает ассеты из `public`: прочитать `node_modules/@opennextjs/cloudflare` или документацию, вывод указать в отчёте. Если всё же пересобирает, предложить другой способ и не делать. В `README.md` строка: после прод-деплоя перед dev-деплоем нужен `npm run cf:build`, так как каталог вырезан. Тест чистой части скрипта, если она есть.

## Итерация 2: способы оплаты

**Данные, `lib/deals/requisites.ts`.** Группы: `bank` (получатель, IBAN, код, ссылка банка: все обязательные поля вместе, ссылка необязательна), `crypto` (USDT TRC-20, Binance ID, подтверждённый адрес кошелька), `foreign` (PayPal, Wise). Минимум один способ, ошибка говорит по-человечески, что заполнить. Для хранения поля остаются плоскими в том же шифрованном JSON, но `recipient`, `iban`, `taxCode` становятся необязательными: старые записи читаются без миграции. Чистая функция `paymentMethods(requisites)` возвращает список включённых способов. `mask`: маска IBAN, а без него короткая метка способа (например, `USDT •••a1b2`), колонка `NOT NULL` остаётся. Снимки сделок, маска, карточка, `dealWalletAddress` не должны падать без IBAN: пройти по всем обращениям к `requisites.iban`, `.recipient`.

**PayPal и Wise.** Флаг `foreign_links` в `lib/features/flags.ts`, в `MONEY_FEATURES` (TOTP и письмо при смене). Строгая проверка: https, без логина и порта, точные хосты `paypal.me`, `www.paypal.com` с путём `/paypalme/<имя>`, `wise.com` с путём `/pay/me/<имя>`; имя из букв, цифр, точки, дефиса и подчёркивания. Без флага поля не сохраняются и не показываются, как `withoutCrypto`. Тесты на чужие хосты, похожие домены (`paypal.me.evil.com`), `http:`, логин в URL.

**Кабинет, `components/requisites/`.** Секция «Як отримувати оплату». Каждый способ отдельная карточка с переключателем: включил, и раскрываются только её поля; выключил, и поля не мешают. Зоны: «Банк», «Крипта», «Закордонні сервіси» (только при флаге); недоступные по флагам не показывать. Сохранение одной кнопкой на всё, ошибки у своего поля. Сохранённое показывается маской, режим ожидания смены с датой. Подтверждение кошелька остаётся в зоне крипты. Логика в хуке. Примитив переключателя добавить в `components/ui` (DS-3), если его нет: Radix Switch, токены, состояния, клавиатура. Форма выплат безопасной сделки отдельна и остаётся как есть, с понятной подписью, чем она отличается.

**Заказчик.**
- `GET /api/deals/config?performer=` дополнить списком `methods` (только названия, без значений). В форме условий строка «Виконавець приймає: …». Нет ни одного способа: прямая сделка всё равно возможна, подсказка договориться.
- Карточка прямого перевода: `transfer-card.tsx` разбить на панели по способам, переключатель (примитив Tabs из Radix в `components/ui`, стрелки, фокус), первый доступный выбран. Один способ: без переключателя. Панели: банк (реквизиты, QR, ссылка), USDT (адрес, QR, хеш), кошелёк (существующая wagmi-панель), Binance ID, PayPal, Wise. PayPal и Wise: кнопка-ссылка с `rel="noopener noreferrer"`, подсказка, что сумму в валюте стороны согласуют в чате и проводит не сайт.
- «Я оплатив(ла)» фиксирует `stage.paidVia` на сервере: значение из разрешённых и только из способов снимка. USDT по хешу и кошелёк пишут его сами. Способ виден исполнителю в подтверждении и модератору.

**Тесты.** Старые реквизиты читаются; только USDT сохраняется, снимок и чтение работают; пустой набор отклоняется; `methods` не содержит значений; чужой `paidVia` отклоняется; способ вне снимка отклоняется.

## Итерация 3: перевірена угода

1. Миграция: `reviews.verified` (`integer`, по умолчанию 0). Чистая функция `isVerifiedDeal(deal, proofs)` в `lib/deals/`: сделка `completed` и каждый этап оплачен подтверждённо: `safe` с `paidAmount`, `escrow` с `paidUnits`, прямой этап с записью в `crypto_proofs`. Для `paidVia` банка, Binance, PayPal, Wise всегда ложь. Флаг ставит только сервер при создании отзыва, из тела запроса не принимается. Старые отзывы не пересчитывать без необходимости: по старым сделкам `verified = 0`.
2. `Review` и API отдают `verified`. В списке отзывов профиля отметка «Перевірена угода» с кнопкой «?» на `popover.tsx`: что она значит. Статистика исполнителя: `verifiedReviews`, показать в профиле рядом с оценкой, карта не меняется. Средняя оценка считается как раньше. `allPerformerStats` и `performerStatsOf` остаются согласованными (есть тест).
3. Тесты: все ветки `isVerifiedDeal`, подделка `verified` в теле, накрутка через прямую сделку без подтверждения даёт `false`.

## Итерация 4: помощь в спорах

Сверить, что уже есть в `app/api/admin/disputes`, `lib/admin/types.ts`, `components/admin`.

1. **Критерии.** Необязательное поле «Що вважаємо готовим» в условиях (до 500 символов), хранится в сделке, не меняется после принятия, видно обеим сторонам (`deal-terms.tsx`) и модератору.
2. **Чек.** На панели прямой оплаты необязательное прикрепление картинки, через существующие вложения чата: `saveChatPhoto`, доступ по той же проверке разговора. `stage.receiptAttachmentId`, виден сторонам и модератору. Подпись: «Необов'язково, але в разі спору це допоможе». Сделка без разговора: скрыть, не ломать.
3. **Результат.** При «здати етап» необязательные текст (до 1000) и ссылка (только https, `rel` как выше): `stage.delivery`. Видны заказчику при приёмке и модератору.
4. **Подсказки.** Компонент «Як уникнути проблем у спорі», сворачиваемый, на `popover` или аккордеоне, в форме условий и на оплате. Коротко: зафіксуйте умови в картці, спілкуйтесь у чаті сайту, зберігайте чек, здавайте результат кнопкою, для великих сум ділите на етапи або беріть безпечну угоду. Текст один, в одном файле, без обещаний, которых нет.
5. **Хронология.** Карточка спора в админке: все метки времени сделки, способ оплаты, транзакция со ссылкой, чек, результат, критерии, маска реквизитов снимка. Чистая функция из сделки в список событий с тестом.
6. **Жалоба по прямой сделке.** Сейчас `dispute` для `direct` отказывает. Кнопка «Поскаржитися» у сторон: причина, текст; таблица `deal_complaints`, лимит частоты, одна открытая жалоба на этап от стороны. Деньги и статус этапа не меняются, в тексте прямо: «Прямий переказ ми повернути не можемо». В админке список жалоб с той же хронологией, закрытие с комментарием, запись в журнал, вторая сторона видит только системное сообщение о жалобе. Публичных отметок нет.

Тесты: неизменность критериев после принятия, чужой чек, чужая жалоба 404, неверная ссылка результата, повтор жалобы.
