## Общие правила для всех исполнителей

- Прочитать `AGENTS.md` и из `.claude/rules/profile/` файлы, подходящие к работе (react-logic, components, semantics, styles, tailwind, testing, cloudflare, forms). `.claude/rules/profile/architecture.md` читать при разбиении модулей.
- Работа в этом клоне, ветка `development`. Перед началом `git status`. Чужое (`concepts/` и всё, что не ваше) не трогать и не добавлять в коммит. Запрещены `git stash`, `reset --hard`, `checkout --`, `clean`, `push`, деплой, применение миграций на удалённые базы, `wrangler secret`.
- Один коммит на итерацию (или несколько логичных), сообщения на украинском, как в истории, только ваши файлы: `git add <пути>`. В конце сообщения строка `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Логика чистыми функциями в `lib/`, эффекты по краям. Функции стрелочные, не больше трёх параметров. Логика компонента в `use-<name>.ts`. Новый UI из `components/ui`; нет примитива, добавить его туда (shadcn/Radix, токены, все состояния, клавиатура, 375 px). Без `motion`, без хардкода цветов, тексты для людей на украинском, комментарии в коде на украинском.
- Секреты только в `.dev.vars` (имена в `.dev.vars.example`), значения не печатать. Новые переменные добавить в типы окружения. Схема БД: править `db/schema*.ts`, затем `npm run db:generate`; применённые миграции не редактировать.
- Перед отчётом: `npm run typecheck`, `npm test`, `npm run lint:ci`. Предупреждения ESLint не растут. Новый тест на исправление обязан падать без него: проверить один раз на важных пунктах.
- Не менять оплату, вход и удаление ради удобства тестов. Банк в тестах подменяется через `fetch`.
- Если решение не описано и ошибка дорога, не гадать, а написать в отчёте вопрос и сделать безопасный вариант.
- Отчёт до 20 строк: коммиты; файлы главными группами; что запущено и с каким результатом; что не проверено; вопросы. Не утверждать то, что не запускали.

## Итерация 5b: контракты

Пункт 24. Папка `contracts/` со своим `package.json` (Hardhat + OpenZeppelin, версии закреплены точно), вне основной сборки: `knip`, `tsconfig`, ESLint её не трогают. Сеть не зашита, адрес токена и получателя комиссии передаются при развёртывании. Без обновлений, без владельца с правом вывода, без `delegatecall` к внешним адресам. `SafeERC20`, потому что USDT нестандартный.

1. `FeeRouter.sol`, прямой платёж с комиссией, деньги в контракте не остаются: `pay(token, recipient, amount, dealRef)` переводит заказчиком одобренную сумму исполнителю и комиссию получателю одной транзакцией, событие с `dealRef`. Ставка в базисных пунктах и получатель неизменяемы, потолок ставки проверяется в конструкторе. Токен из неизменяемого белого списка конструктора.
2. `EscrowFactory.sol` + `DealEscrow.sol` (минимальные клоны, EIP-1167, через CREATE2): **отдельный контракт на каждую сделку**, чтобы заморозка адреса или ошибка не задели остальных. Параметры при создании: заказчик, исполнитель, сумма, сроки, `dealRef`; ставка, получатель комиссии, арбитр, токен и лимит на сделку от фабрики, неизменяемы. Заказчик вносит токен; исполнитель `deliver`; заказчик `release`; по таймеру после сдачи деньги уходят исполнителю, без сдачи возвращаются заказчику; спор открывает любая сторона, `resolve` только арбитр и только процентом между этими двумя адресами, кратным 5 %. Арбитр не может забрать деньги себе и не может действовать без спора. При споре таймеры не срабатывают, но после длинного срока без решения любая сторона может вернуть деньги по правилу из конструктора.
3. **Заблокированный адрес.** USDT умеет блокировать адреса. Выплата заблокированному исполнителю не должна запирать деньги навсегда: тест с токеном-заглушкой, у которого `transfer` падает для отдельного адреса, и путь выхода через спор. Комиссия не должна мешать выплате: отказ перевода комиссии не блокирует основного получателя.
4. Тесты: токен без возвращаемого значения (как USDT), все ветки и сроки, повторный вход, чужой вызывающий, инвариант «сумма выплат равна внесённому», фаззинг сумм на границах округления. Статический анализ, если ставится без внешней установки; иначе написать, что не запускался.
5. `contracts/scripts/deploy.ts` читает параметры из окружения и не содержит ключей. README: что контракты не проверены аудитом и как развернуть. **Развёртывание в любую сеть запрещено исполнителю**, только локальная сеть Hardhat. ABI и адреса-заглушки отдать в `lib/crypto/abi/` для итерации 5c.

## Итерация 5c: кошельки (wagmi)

Пункты 27, 28, 29. Флаги `crypto_wallet` и `crypto_escrow`. Зависит от 5a и 5b. Сеть и адреса задаются в окружении (`CRYPTO_CHAIN_ID`, `CRYPTO_TOKEN_ADDRESS`, `CRYPTO_ROUTER_ADDRESS`, `CRYPTO_FACTORY_ADDRESS`, `CRYPTO_RPC_URL`, `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID`). Нет адреса: функция считается выключенной независимо от флага. Адрес токена не брать из памяти: заглушка в `.dev.vars.example` и напоминание сверить со страницей Tether.

1. **Подключение.** `wagmi`, `viem`, `@tanstack/react-query`, версии закреплены точно. Сверить актуальную версию и настройку SSR по `wagmi.sh`. Коннекторы `injected`, `metaMask`, `walletConnect`; холодные кошельки подключаются через них. **Только динамический импорт в компоненте оплаты**: на главной и карте ни байта wagmi, проверить по выводу сборки. Своя кнопка и список кошельков на `components/ui`, без готовых модальных окон.
2. **Пункт 27, адрес исполнителя.** Подпись сообщения с `nonce`, сроком и доменом кошельком; сервер проверяет подпись через `viem`, адрес попадает в реквизиты и снимок сделки как подтверждённый. Смена адреса идёт через те же 24 часа.
3. **Пункт 28, прямой платёж из кошелька.** Заказчик видит адрес и сумму, подтверждает в кошельке. Одобрение только на точную сумму, никогда не бесконечное. Без комиссии: `transfer` токена. С комиссией: `FeeRouter`, две транзакции, если нужно одобрение. Хеш уходит на сервер, сервер читает квитанцию через `CRYPTO_RPC_URL`, сверяет сеть, контракт, получателя, сумму, число подтверждений и уникальность хеша, затем `claimed`. Подтверждает исполнитель, как в 5a, а через `FeeRouter` с точной суммой этап сразу `funded`.
4. **Пункт 29, эскроу.** Новый `method` сделки `escrow`, сумма этапа в USDT фиксируется при принятии. **Истина в блокчейне:** статус этапа сервер ставит только чтением состояния контракта, в `deal-sweep` добавить сверку. Кошелёк заказчика подписывает внесение и приёмку, кошелёк исполнителя сдачу. Решение спора: показать в админке точные данные для мультиподписи (`Safe`), сервер ключей не хранит и транзакций не подписывает.
5. Неверная сеть, отказ в кошельке, транзакция отменена или заменена, кошелёк закрыт посреди операции, нет газа: у каждого состояния понятный текст. Перед подтверждением показать адрес целиком и попросить сверить на устройстве.
6. Тесты: чистые функции разбора и сверки с подменой RPC, поддельная квитанция, чужой токен, повтор хеша, просроченная подпись, чужая подпись. UI на `mock`-коннекторе wagmi. Сквозной сценарий против локальной сети Hardhat из `contracts/`, если поднимается без внешних ключей.
