## Goal

Заказчик прикладывает к запросу настоящие файлы (раньше сохранялись только имя, размер и тип, кнопку скрыли, R-1 из ревью, решение 2 владельца). Файлы лежат в R2, исполнитель видит список в карточке запроса и открывает файл, доступ проверяется так же строго, как к самому запросу, гость файлов не видит.

## Decisions

- Файл грузится до сохранения запроса и привязывается по id (как фото чата), а не после публикации: так публикация остаётся одним запросом, чернетка переживает вход, ошибки видны сразу. Цена: таблица `request_files` с необязательным `request_id` и чистка осиротевших. (why: образец чата, один запрос публикации)
- Одна таблица, пересоздание через миграцию (`request_id` стал nullable), а не вторая таблица загрузок. Drizzle сгенерировал `__new_request_files` → `INSERT … SELECT` → `DROP` → `RENAME`; на `request_files` ни одна таблица не ссылается, поэтому `DROP` на D1 безопасен. Старые строки копируются с `key = null`. (why: один id для всех файлов запроса, проще логика)
- Старые строки без `key` остаются и показываются названием без ссылки («вміст не збережено»), а не удаляются. (why: данные не теряем молча; удалить можно отдельным решением)
- Скрепка только для вошедших: загрузка требует сессии, а у гостя вход идёт после «Знайти виконавців» (в том числе через Google с перезагрузкой, где файлы потерялись бы). Гость добавит файлы в «Редагувати запит» после публикации. (why: честнее, чем кнопка, ведущая на вход и теряющая текст)
- Одна кнопка вместо меню «Файл / Зображення / Код»: меню вело к одному и тому же вводу файла, различалось только `accept`; подпись у кнопки прежняя, «Додати файл, зображення або код». (why: меньше UI, меньше CSS, то же поведение)
- Доступ к файлу: автор; исполнитель с опубликованным профилем, пока запрос открыт (как лента и карта); откликнувшийся исполнитель, в том числе после закрытия запроса; остальные получают 404, гость 401. Нет отдельной проверки `channel_opt_in`, потому что лента и карта его тоже не проверяют. (why: «как к самому запросу»)
- `FeedItem.files` необязательное поле: `components/maplibre/maplibre-scene.tsx` (`ownRequestOnMap`) собирает `MapRequest` вручную, а трогать `maplibre` задача запретила. Свой запрос на карте файлов не несёт, автор видит их в деталях. (why: ограничение задачи; чтобы поле стало обязательным, достаточно добавить `files: request.files` в `ownRequestOnMap`)
- Лимиты: 8 МБ на файл, 10 файлов и 25 МБ на запрос, 20 несвязанных загрузок на человека, правило частоты `upload` (30 за 10 минут). Типы: изображения (jpg, png, webp, gif), pdf, docx/xlsx/pptx/zip, текст и код (список в `file-types.ts`). Всё отдаётся как скачивание, кроме картинок. (why: потолок памяти воркера, безопасность выдачи)

## Not verified

- Реальный R2 на dev и prod: только `getPlatformProxy` (miniflare) в тестах и локальный wrangler в dev-сервере.
- Миграция 0029 на удалённой D1 (dev, prod): не применялась. Применилась на локальной D1 и in-memory. Перед prod стоит снять копию таблицы `request_files` (пересоздание таблицы).
- Карточка запроса у исполнителя (`FeedCard`, список файлов): в браузере не открывалась, нужен второй аккаунт с опубликованным профилем; покрыто тестами данных (`FeedItem.files`) и компилятором.
- Экран «Редагувати запит» с файлами: в браузере не открывался (логика проверена тестами PATCH и хука).
- Выбор файла настоящим диалогом ОС: файлы подставлялись в скрытый input скриптом (`DataTransfer`), диалог не вызывался. Реальные загрузки крупных файлов (8 МБ) в браузере не пробовались.
- Тёмная тема, 768 и 1024 px, Safari/Firefox.
- Полный прогон `npm test` два раза из четырёх уронил один и тот же тест `feed-city-paging.test.ts` («больше 200 запросов»), при нагрузке от других сессий; в изоляции этот файл зелёный (16 из 16, 7 с). Причину по таймауту не доказывал (в тесте нет файлов, лишних запросов моя правка не добавляет: `hydrate` читает файлы тем же одним запросом), вероятнее всего это нагрузка машины.
